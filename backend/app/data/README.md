# Road network data — provenance

## Current dataset: real, branched OSM road network

The active dataset is `guwahati_tawang_osm_corridor.geojson` — a real
OpenStreetMap road-network extract for the Guwahati → Tawang corridor,
supplied directly (not generated by a script in this repo). It is a
GeoJSON `FeatureCollection` of ~2,000 OSM way LineStrings, each carrying
real tags: `osm_id`, `name`, `highway`, `ref`, `oneway`, `maxspeed`.

It is loaded and converted into this project's graph at **runtime** (not
pre-baked into an intermediate JSON) by two modules in `app/data/`:

1. `osm_geojson_loader.py` — generic OSM-GeoJSON → `Node`/`RoadSegment`
   converter. Knows nothing about "Guwahati" or "Tawang" specifically; a
   different NER-region GeoJSON extract can be substituted by pointing
   `network_loader.py` at a new file and a new named-locations list,
   without touching this module or `core/routing_engine.py`.
2. `network_loader.py` — the corridor-specific integration point: points
   the generic loader at `guwahati_tawang_osm_corridor.geojson` and at the
   7 demonstration locations in `demo_locations.py`.
3. `demo_locations.py` — the 7 demonstration locations (Guwahati, Tezpur,
   Bhalukpong, Bomdila, Dirang, Sela Pass, Tawang), each matched to its
   nearest real graph node ("nearest-node resolution") and tagged with a
   friendly name — the *only* file that hardcodes this specific corridor.

`core/routing_engine.py` never parses GeoJSON, never sees a `highway` tag,
and never sees a coordinate list from a raw feature — it only ever consumes
`Node`/`RoadSegment` objects and the `networkx.DiGraph` built from them.

### Why runtime parsing works here

Loading and converting the ~2.9MB GeoJSON (≈2,000 features, ~90k coordinate
points) into the full node/edge graph takes well under a second — see the
implementation report for actual numbers. There's no need for an
intermediate pre-built JSON file the way Part 2/3's OSRM-derived dataset
needed one (that data came from live external API calls; this data is
already a static local file).

### Topology: how the graph is actually built

A real OSM way's LineString often runs *through* another way's
intersection without an explicit shared endpoint — a side road's
T-junction onto a highway is typically a point in the *middle* of the
highway's coordinate list, not at either way's start/end. So the loader:

1. Finds every coordinate that is either a way's own endpoint, or shared
   (to 6 decimal places, ≈0.11m) with another way's coordinate — a real
   intersection.
2. Splits each way's LineString into one edge per run between consecutive
   such points.

That splitting is what produces genuine branching in the resulting graph.

### oneway handling

`core/routing_engine.py::build_graph()` builds a **directed** graph
(`networkx.DiGraph`). Each `RoadSegment` becomes one directed edge
`from_node_id → to_node_id`, plus an additional reverse edge **only if**
`segment.bidirectional` is `True`. A segment is marked `bidirectional=False`
(one-way) **only when its raw OSM `oneway` tag is exactly `"yes"`** — every
other value (`None`, `"no"`, `"reversible"`, or anything else) stays
bidirectional. No one-way restriction is ever invented; the graph only
encodes what the `oneway` tag actually says.

### What is real vs. derived vs. not-yet-assessed

Every segment's `"source"` block in the API states this per field. Summary:

| Field | Status | Source |
|---|---|---|
| Node `lat`/`lng` | **Real** | OSM coordinates, straight from the GeoJSON |
| Segment `geometry`, `distance_km`, `road_type`, `name`, `ref`, `oneway`, `maxspeed`, `osm_way_ids` | **Real** | OSM way tags/geometry, straight from the GeoJSON |
| Segment `estimated_travel_time_min` | **Real distance, real-or-assumed speed** | `distance_km` is a real haversine sum over real coordinates. Speed is the tagged `maxspeed` where parseable, otherwise a highway-class default (`osm_geojson_loader.DEFAULT_SPEED_KPH`) — exposed as `assumed_speed_kph` so the assumption is never hidden |
| `elevation_m`, `terrain_type` | **Derived (approximated)** | Each segment is assigned the elevation of whichever of the 7 demonstration towns its midpoint is nearest to (real measured elevation for those 7 towns — Open-Elevation/SRTM, Part 2), then bucketed into plain/hill/mountain by threshold. A coarse step-function approximation, not a per-segment measurement |
| `landslide_susceptibility`, `flood_susceptibility` | **Not assessed** | Uniformly `0.0` for every segment — no real hazard-zonation dataset is available yet. Hand-varying these across thousands of segments would be indistinguishable from fabrication, so they're explicitly left at a neutral "unknown" value instead |
| `base_risk` | **Derived** | The existing formula (`core/risk_engine.py::compute_base_risk`), which reduces to the terrain-only component since susceptibility factors are 0 |

### What needs to be replaced before any real-world hazard claim

`landslide_susceptibility`, `flood_susceptibility`, and by extension
`base_risk`, need real hazard-zonation data before this system means
anything beyond a demo — e.g. GSI Bhukosh/BhuVigyan landslide
susceptibility layers, NRSC/CWC flood hazard atlases.
`elevation_m`/`terrain_type` should eventually come from a real DEM sampled
per segment rather than the nearest-town approximation described above.

### Limitations discovered

- **Assumed speeds are conservative.** Only ~4% of ways in this extract
  carry a `maxspeed` tag; the rest fall back to flat highway-class
  defaults that don't account for mountain hairpins/gradient (e.g. the
  Dirang → Sela Pass climb). Estimated travel times on the mountain
  sections are likely overestimates of free-flow time and underestimates
  of real-world time (which is dominated by switchbacks, not distance).
- **`oneway=reversible` is treated as bidirectional.** A real reversible
  road is direction-restricted at certain times, which this static graph
  can't represent — see `osm_geojson_loader.py::_is_bidirectional`. Only 3
  segments in this dataset carry that value.
- **The raw extract has ~22 small disconnected fragments** (2-6 nodes each,
  ~2% of nodes total) at its geographic boundary — roads cut off mid-way by
  the extraction area. All 7 demonstration towns are confirmed to sit in
  the single large connected component (see
  `tests/test_network.py::test_demonstration_towns_share_one_connected_component`);
  the small fragments are simply unreachable dead ends, not a routing bug.
- **Parallel duplicate ways are collapsed.** Where two different OSM ways
  connect the exact same two intersection nodes (e.g. separately-digitized
  carriageways of a divided highway), only the shorter is kept — the graph
  model here is one edge per node pair, not a multigraph.
- Non-`"yes"` oneway values (`-1`, `alternating`, etc.) don't happen to
  appear in this extract; if a future dataset includes them, they are
  *not* specially handled and are treated as bidirectional under the same
  rule as any other non-`"yes"` value. Flagged here in case that matters
  for a different NER dataset later.

## GSI landslide inventory: spatial join to road segments

`gsi_landslides_corridor.csv` (and the wider `gsi_landslides_arunachal.csv`,
not yet used) is a real GSI field-validated landslide inventory extract:
`slide_no`, `slide_id`, `state`, descriptive text, `latitude`/`longitude`
(WGS84 decimal degrees), `raw_record`.

`landslide_mapper.py` spatially joins each landslide to its nearest real
OSM road segment (both reprojected to a UTM zone estimated from the road
network's own extent — never a raw-degree distance), keeping a record
UNMATCHED (not discarded) if the nearest road is more than 500m away. Run
it with `cd backend && python -m app.data.landslide_mapper`; it writes:

- `derived/gsi_landslides_corridor_mapped.csv` / `.geojson` — every source
  record, unchanged, plus `distance_to_road_m`, `matched_segment_id`,
  `matched_road_name`, `matched_highway_class`, `match_status`.
- `derived/road_landslide_features.csv` — one row per current road
  segment: `historical_landslide_count` (0 if none — not deduplicated,
  repeated GSI observations near the same point each count) and
  `nearest_landslide_distance_m` (null when count is 0).

**This is a historical count, not a risk score or a probability.**
`RoadSegment.historical_landslide_count` /
`.nearest_landslide_distance_m` are informational fields only — nothing in
`core/risk_engine.py` or `core/routing_engine.py` reads them yet, and the
baseline routing cost is still travel time only. They exist so a later step
can combine them with slope/elevation/rainfall/weather/field incidents into
an actual ML training dataset — that combination hasn't happened yet.

This CSV covers a wider area than just this corridor (some records are
100+ km away, e.g. the Anjaw-Tezu stretch of NH-13, a different part of the
highway than our Guwahati-Tawang section) — expect a meaningful fraction of
records to be genuinely UNMATCHED, not a pipeline bug.

### Validating the mapped dataset against the network's real extent

`landslide_corridor_validation.py` is a separate, read-only pass over the
already-mapped CSV above — it does not change the 500m matching threshold,
routing, or the risk engine. It checks each record against two independent
geographic facts about the real network: is it within the network's own
bounding box, and (for matched records) does its matched segment actually
sit on the same connected road network as the 7 demonstration towns, or on
one of the ~22 small disconnected fragments at the extraction boundary?
Run it with `cd backend && python -m app.data.landslide_corridor_validation`;
it writes `derived/gsi_landslides_osm_corridor.csv` — the MATCHED subset
only (still the 500m threshold, just filtered to it), confirmed
geographically consistent by both checks, with `district`/`movement_type`
added (best-effort text extraction from the free-text description columns
— see the module docstring for the header-artifact caveat found in a few
source rows).

## DEM provenance: real elevation and slope (Part 4.8)

`elevation_m` and `slope_deg` on every `RoadSegment` are now sampled from a
real Digital Elevation Model, replacing the old 7-point nearest-town
step-function approximation described earlier in this file (that
approximation is kept only as an explicit, labelled fallback — see below).

### Source

- **Dataset**: "Terrain Tiles", published on the AWS Registry of Open Data
  (https://registry.opendata.aws/terrain-tiles/), "skadi" layout.
- **Underlying data**: NASA SRTM (Shuttle Radar Topography Mission)
  1-arc-second global elevation, void-filled by the dataset's own
  build pipeline (Tilezen/Joerd) using auxiliary sources where SRTM itself
  has gaps.
- **Format**: standard `.hgt` SRTM1 tiles — one file per 1°x1° cell, 3601 x
  3601 samples, big-endian signed 16-bit integers, gzip-compressed on the
  server.
- **Resolution**: 1 arc-second, ≈30m at this latitude.
- **CRS**: WGS84 geographic coordinates (EPSG:4326); elevation values are
  heights above the EGM96 geoid (SRTM's native vertical datum) — not
  ellipsoidal height.
- **Access**: public, unauthenticated HTTPS, no API key required —
  `https://s3.amazonaws.com/elevation-tiles-prod/skadi/{tile[:3]}/{tile}.hgt.gz`.

### Coverage and download

The corridor's real bounding box (lat 26.01-27.75, lon 91.54-92.98) is
covered by exactly 4 tiles: `N26E091`, `N26E092`, `N27E091`, `N27E092`.
These were downloaded once with a plain `curl` against the URL pattern
above and are cached as their original `.hgt.gz` files under
`backend/app/data/dem_cache/` (see `dem_loader.py`) — loaded from local
disk at runtime, not re-fetched on every run, the same reasoning already
applied to the supplied OSM GeoJSON extract. Each file was verified to
decompress to exactly 25,934,402 bytes (3601 x 3601 x 2), confirming a
genuine SRTM1 tile rather than a truncated/corrupt download.

### Preprocessing and sampling method

1. Each `RoadSegment`'s real OSM geometry is resampled at ~90m spacing
   (`dem_processor._resample_line`) — every original vertex is kept, with
   extra interpolated points added along any edge longer than the
   interval, so a long or winding segment gets many real DEM samples, not
   just its two endpoints.
2. Each resampled point is bilinearly interpolated from the surrounding 4
   DEM grid cells (`dem_loader.DemTile.elevation_at`). A grid cell holding
   the SRTM void sentinel (-32768) is never blended into a real-looking
   number — the void-aware fallback uses the single nearest valid corner,
   or returns nothing for that point.
3. **Representative `elevation_m`** = the mean of all successfully sampled
   elevations along the segment.
4. **`slope_deg`** = the *mean absolute gradient magnitude* over the
   sampled profile:
   `slope_percent = (sum of |elevation change| between consecutive valid
   samples) / (total horizontal distance between them) * 100`, then
   `slope_deg = degrees(atan(slope_percent / 100))`. This is deliberately
   **not** simple `(end elevation - start elevation) / distance`: a
   mountain segment that climbs and then descends within itself would
   otherwise report a falsely flat slope just because its two endpoints
   happen to sit at similar elevation. Summing absolute changes means
   climbs and descents both contribute, so undulating terrain is reflected
   in the number. `slope_deg` is therefore a magnitude (always ≥ 0), not a
   directional grade.
5. `slope_deg` is left `None` when fewer than 2 valid DEM samples exist
   along a segment (nothing to compute a gradient from).

See `dem_loader.py` and `dem_processor.py` module docstrings for the full
implementation detail, and `dem_validation.py` (`python -m
app.data.dem_validation`) for the coverage/statistics report referenced
below.

### Fallback behaviour (honest labelling, not silent substitution)

If a segment's geometry falls outside the 4 cached tiles, or every sampled
point along it hits a void, `elevation_m` falls back to the pre-4.8
nearest-reference-town approximation and `slope_deg` is left `None` for
that segment. `RoadSegment.source["elevation_m"]` says `"fallback: ..."` in
that case — it never claims a real per-segment DEM measurement it doesn't
have. In practice, running the validation script shows **0 of 2,964
segments** used this fallback for this corridor — full real-DEM coverage.

### Validation results (see `dem_validation.py` for how to reproduce)

- 2,964 / 2,964 segments (100%) got a real DEM-sampled elevation and slope.
- Elevation range: ~46m (Brahmaputra plains near Guwahati) to ~4,499m
  (near Sela Pass) — median ~60.5m (most of the corridor's segment *count*
  is in the flatter Assam portion).
- Slope range: 0.00° to 29.87°, median 1.31°.
- Sample values near each named location (nearest segment, real DEM):
  Guwahati ≈60m, Tezpur ≈81m, Bhalukpong ≈176m, Bomdila ≈2,428m, Dirang
  ≈1,632m, Sela Pass ≈3,733m, Tawang ≈2,904m — a clear, real elevation
  gradient the old 7-fixed-point approximation could only ever reproduce
  at those exact 7 spots, never for the thousands of segments between them.

### Known limitations

- **Tunnels are not special-cased and will show misleadingly high slope.**
  This GeoJSON extract's OSM tags do not include `tunnel`/`bridge`
  (`osm_geojson_loader.py` only ever reads `highway`/`name`/`ref`/
  `oneway`/`maxspeed` — see its module docstring), so a way like the real
  "Sela Tunnel" (NH13, bored through the mountain near Sela Pass) is
  treated like any surface road: the DEM reports the *mountain's surface
  elevation above the bore*, not the tunnel's actual (much gentler,
  engineered) interior grade. Two Sela Tunnel segments are among the
  validation report's "suspicious slope" flags (~26-30°) for exactly this
  reason — this is a genuine methodological limitation of surface-DEM
  sampling applied to underground infrastructure, not a bug in the
  sampling code. A future dataset extract that carries the `tunnel`/
  `bridge` tags could special-case these (e.g. by using a straight-line
  interpolation between portal elevations rather than surface DEM values).
- **A void-filled global DEM is not survey-grade.** ~30m horizontal
  resolution and SRTM-era vertical accuracy (roughly ±10-16m in mountainous
  terrain) mean `elevation_m`/`slope_deg` are good per-segment terrain
  *features*, not precision engineering measurements.
- **The 90m resampling interval can still miss very sharp, sub-90m
  switchbacks.** A hairpin tighter than the sampling interval is smoothed
  over; the reported slope for such a segment is a reasonable average, not
  a peak/instantaneous grade.
- **One flagged segment ("Eaglenest road", ~13m long, ~29° slope) is very
  short** — a single tight real switchback link, not a tunnel or an
  obvious data error, but short segments amplify sampling noise more than
  longer ones; treat single-digit-meter segments' slope with some caution.

### Terrain features are not hazard susceptibility

To restate what's already true elsewhere in this file: `elevation_m` and
`slope_deg` are real terrain measurements. They are **not** a landslide
probability, a risk score, or a hazard assessment on their own.
`landslide_susceptibility`/`flood_susceptibility` remain uniformly `0.0`
(no real hazard-zonation dataset exists yet — see above), and
`base_risk`/`current_risk_score` still do **not** read `slope_deg` — that
wiring is explicitly out of scope for Part 4.8 (data preparation only).

## Part 5: explainable prototype risk engine

`core/risk_engine.py::assess_segment_risk()` is a new, separate scorer
built on top of the real data documented above. Full methodology lives in
that module's docstring, `app/config.py` (every tunable constant, each with
its own reasoning comment), and `app/models/risk.py` (the `RiskResult`/
`RiskBreakdown` output shape) — this section is a short pointer/summary,
not a duplicate of that detail.

**What it is**: `risk_score = clamp(0.35*slope_risk + 0.35*historical_landslide_risk
+ 0.20*weather_risk + 0.10*incident_risk, 0, 1)`, plus a `risk_level`
(low/moderate/high/critical) and a plain-language `reasons` list. It is a
**rule-based weighted combination**, explicitly called an "explainable
prototype risk score" everywhere it's surfaced — never a calibrated
probability (see `backend/app/data/training_dataset_schema.md` for exactly
what training data would be needed before any ML-calibrated version could
exist).

**What it is NOT**: it does not replace or change
`RoadSegment.base_risk`/`current_risk_score` (Part 2's terrain-only
formula, still used by `osm_geojson_loader.py` and the existing
`/segments/{id}/risk` endpoint), and it is not wired into routing cost,
rerouting, or any PROCEED/REROUTE/SUSPEND logic — `core/routing_engine.py`
still costs edges by travel time only.

**Slope component**: real DEM `slope_deg` (Part 4.8), linear-normalized
between 2° (treated as flat) and 25° (saturates at 1.0 — matches
`dem_validation.py`'s own "suspicious slope" threshold for this corridor).
Slope is a terrain feature, not a landslide probability by itself.

**Historical landslide component**: real GSI-matched
`historical_landslide_count`/`nearest_landslide_distance_m` (the spatial
join described above), combined as `0.7 * log-scaled count-score + 0.3 *
proximity-score`. The log scaling means the single most-observed segment
in the corridor (11 matched records) does not get ~11x the contribution of
a segment with 1 — it saturates at 5 matched observations. **`count == 0`
always scores 0.0 and is never treated as "confirmed safe"** — every
`RiskResult` for such a segment explicitly says so in its `reasons` (only
104 of ~2,964 segments have any matched GSI record at all).

**Weather / incident components**: both are externally supplied `[0,1]`
factors (`weather_factor`, `incident_factor`), defaulting to `0.0` when not
supplied. Neither is a trained/rainfall-based prediction — no historical
rainfall dataset exists yet (that's later scope). A default of 0.0 means
"no signal supplied," never "confirmed clear/no incident."

**Reproduce the real-corridor examples**: `cd backend && python -m
app.data.risk_engine_validation` — prints the prototype score/breakdown for
the nearest real segment to each of the 7 named locations, the 5
highest-scoring real segments in the corridor, and a weather/incident
sensitivity demo on the top one. Nothing in that script's output is
hard-coded; every number comes from the live DEM+GSI-derived RoadSegment
data.

## History: the Part 2/3 OSRM-derived single-chain dataset

The original dataset (Part 2/3) was a hand-picked chain of exactly 7 towns
and 6 town-to-town OSRM route legs — sufficient for baseline routing, but
not for genuine alternative-route comparison (it was, by construction, a
single path with no branches). It's fully superseded by the real GeoJSON
dataset above. Its generation scripts are kept in `backend/scripts/` for
history only (not called by the running app or by anything in `app/data/`):

1. `fetch_corridor_data.py` — Nominatim geocoding + Open-Elevation +
   OSRM route legs for the 7 named towns only.
2. `build_seed_network.py` — converts that cache into the old single-chain
   JSON shape.

An intermediate attempt to build a branched network via OSMnx/Overpass
(rather than a supplied GeoJSON) turned out to be too slow/unreliable
against free public Overpass mirrors from this environment and was
abandoned in favor of the directly-supplied GeoJSON used above.
